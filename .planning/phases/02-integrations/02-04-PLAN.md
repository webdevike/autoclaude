  <name>Task 1: Initialize extensions in createMinimalResourceLoader</name>
  <files>packages/core/src/pi-session.ts</files>
  <action>
In `createMinimalResourceLoader`, the `extensions` parameter receives raw extension factory functions from agent.ts. These are `(pi: ExtensionAPI) => void` functions. Currently `createExtensionRuntime()` creates the runtime but the factory functions are never called, so `pi.registerTool()` and `pi.on('session_start', ...)` never execute.

**The fix is simple.** Extensions are just functions. Call them with `runtime.api`. That triggers their internal `pi.registerTool()` and `pi.on()` registrations. Then `createAgentSession` handles the rest.

Add a loop after `createExtensionRuntime()` and before the `return` block:

```typescript
function createMinimalResourceLoader(systemPrompt: string, extensions: any[] = []): ResourceLoader {
  const runtime = createExtensionRuntime();

  // Initialize extensions - call each factory with runtime.api
  for (const ext of extensions) {
    if (typeof ext === 'function') {
      try {
        ext(runtime.api);
        console.log('[pi-session] Loaded extension');
      } catch (err) {
        console.error('[pi-session] Failed to load extension:', err);
      }
    }
  }

  return {
    getExtensions: () => ({ extensions, errors: [], runtime }),
    // ... rest unchanged
  };
}
```

**What NOT to do:**
- Do NOT import `loadExtensionFromFactory` -- it is an SDK internal, may not be exported, and is unnecessary here.
- Do NOT make `createMinimalResourceLoader` async -- not needed.
- Do NOT try to convert functions to Extension objects -- just call them.
- Do NOT import `createEventBus` -- not needed.
- Do NOT manually emit `session_start` -- `createAgentSession` handles lifecycle events.

No new imports needed. The function signature stays synchronous. The `getExtensions` return stays the same.

**Data flow after fix:**
```
agent.ts: EXTENSIONS = [gmailExtension, exaExtension, ...] (factory functions)
  -> createPiSession({ extensions: EXTENSIONS })
  -> createMinimalResourceLoader(prompt, EXTENSIONS)
  -> ext(runtime.api) for each -- triggers pi.registerTool() and pi.on() registrations
  -> createAgentSession picks up registered tools and handlers
  -> session_start fires automatically, extensions initialize API clients
  -> Extension tools available to agent
```

<task type="auto">
  <name>Task 2: Fix tmux window cleanup in coding delegation</name>
  <files>packages/core/src/coding-delegate.ts</files>
  <action>
The `killTmuxWindow` function (line 56) runs `spawnSync('tmux', ['kill-window', '-t', 'jarvis-agents:${windowName}'])` but:
- The `stdio: "ignore"` swallows all output including errors
- The return status is never checked
- The try/catch only catches JS exceptions, not tmux command failures (spawnSync doesn't throw on non-zero exit)

Fix the `killTmuxWindow` function:

1. Remove `stdio: "ignore"` and use `stdio: "pipe"` instead so we can capture stderr
2. Check the `status` property of the spawnSync result:
   ```
   function killTmuxWindow(windowName: string): void {
     const result = spawnSync("tmux", ["kill-window", "-t", `jarvis-agents:${windowName}`], {
       stdio: "pipe",
     });

     if (result.status === 0) {
       console.log(`[coding-delegate] Killed tmux window: ${windowName}`);
     } else {
       const stderr = result.stderr?.toString().trim() || "unknown error";
       console.warn(`[coding-delegate] Failed to kill tmux window '${windowName}': ${stderr}`);

       // Diagnostic: check if session exists but window name is wrong
       const hasSession = spawnSync("tmux", ["has-session", "-t", "jarvis-agents"], { stdio: "ignore" });
       if (hasSession.status === 0) {
         const listResult = spawnSync("tmux", ["list-windows", "-t", "jarvis-agents", "-F", "#{window_name}"], { stdio: "pipe" });
         const windows = listResult.stdout?.toString().trim() || "";
         console.warn(`[coding-delegate] Current windows: ${windows}`);
       }
     }
   }
   ```

NOTE: The diagnostic logging (session check + window listing) helps identify the root cause for a proper fix later. It reveals whether the issue is a wrong window name, missing session, or something else entirely.

This ensures:
- Failures are logged with stderr details instead of swallowed silently
- We can diagnose WHY the window persists (wrong target format, session gone, etc.)
- No behavior change on success path
